# v0.1 specification gap assessment

Assessment date: 15 October 2026. Requirements baseline: the owner's confirmed
grilling interview in this chat, Q1–Q43 and subsequent corrections. This report
records that agreed baseline; it does not silently replace FUNCTIONAL_SPEC.md.

Source snapshot: shared checkout `codex/credential-separated-member-execution`,
commit `405c89e`, initially clean. The separate
`/private/tmp/commonroom-scoped-tool-audit-callbacks` worktree remains based on
`fc6da1b` with staged, newer audit hardening and unstaged documentation additions.
Those worktrees are different deliverables, not interchangeable validation evidence.
Private repository documentation was sampled at default-branch revision
`2f47977a144249090d0f87dabf179ce1e52a50b6`; its full source/test suite was not audited.

## Finding

The repository has substantial collaboration, security and explicit recovery
foundations, but does not yet deliver the agreed v0.1 agent-development journey.
The immediate blocker is a build failure. The largest functional blocker is the
unintegrated credential-separated provider/tool runtime. Governing-agent
delegation, general approval/disagreement transitions, llama.cpp and automatic
recovery are also unfinished. Existing rooms, personas, hierarchy, immutable event
storage and manual recovery should be extended rather than rebuilt.

No completion percentage or delivery estimate is defensible from this inspection.
Components passing synthetic tests are not equivalent to a verified release path.

## Agreed release boundary

- Free, open-source, single-human harness with rooms, multiple agents per
  connection, personas and a replaceable governing agent, initially the first
  connected agent. Supported required connections: Claude CLI, Codex CLI and
  llama.cpp. Existing CLI subscriptions remain supported; no silent API-billing switch.
- Human-authorized delegation and mandatory isolated execution. Irreversible
  external actions require announced, explicit approval; silence never approves.
  Disagreement blocks affected tasks pending the human, while independent work
  can continue. Decisions, instructions, approvals and results must be traceable.
- Self-hosted controller/browser and supported local/remote workers. A genuinely
  free hosted service is targeted but may slip. User-controlled workers retain
  provider credentials; hosted chat/task/audit/result storage is permitted.
- Automatic recovery is desired, reusing duplicate prevention and reconciliation;
  this does not settle every ambiguous-side-effect retry policy.
- MCP and skills appear as **coming soon**. Full extension execution is not a
  v0.1 blocker. Paid multi-human operation, majority consensus after hearing
  dissent, configurable escalation, delegated authority limits, Fulginn and
  Veriscribe belong to separate private development. Reuse the existing company
  hierarchy. SOC 2 readiness is a future enterprise objective, not a current claim.

## Immediate build and audit integration findings

Shared snapshot compilation fails at:

- `cmd/server/agents.go:40` and `:611`: `providerTurnArgs` receives two arguments;
  the current signature requires three.
- `cmd/server/remote_worker.go:542` and
  `cmd/server/credential_boundary_test.go:13`: callers pass an additional boolean
  to `localIsolatedDevelopmentCommand`, whose signature has not gained that parameter.

These are verified baseline failures, not findings from live execution. No
launch code was changed during this assessment.

Despite its title, commit `405c89e` does not contain all the hardened audit slice:

- The staged branch generates/pins a random per-link session nonce; shared
  `internal/toolbroker/audit_stream.go` does not.
- The staged branch persists managed-job `InitiatorID`/`CompanyID` and checks them
  on acknowledgements; shared `managed_jobs.go` and `tool_audit.go` omit that binding.
- The staged controller rejects a new intent while another is unresolved; shared
  code only counts calls and checks reused IDs.
- The staged branch supplies `serveToolAudit`; shared code has no such assembly method.
- Shared `newToolDispatcher` still constructs `storedToolAuditor`, independently
  of `controllerToolAuditor`, and has no production caller.

Compare [shared stream](../internal/toolbroker/audit_stream.go),
[shared controller](../cmd/server/tool_audit.go),
[shared assembly](../cmd/server/tool_broker.go) against the staged files in the
separate audit worktree. Hardened component tests there must not be reported as
evidence that the shared runtime has those guarantees. Agree integration with
the runner owner; do not copy stale duplicate implementations or remove the
mandatory admission barrier.

## Private commercial boundary and specification drift

Both repositories are accessible under `Daemon-Labs-Co`:
[public harness](https://github.com/Daemon-Labs-Co/agent-commonroom) and
[private commercial services](https://github.com/Daemon-Labs-Co/commonroom-commercial-services).
The private repository's [paid-feature contract](https://github.com/Daemon-Labs-Co/commonroom-commercial-services/blob/2f47977a144249090d0f87dabf179ce1e52a50b6/docs/premium-features.md)
describes issuer-signed entitlements plus owner flags for protected archive and
managed orchestration. It explicitly reports both integration routes as HTTP 501;
checkout, issuer service, archive export, metering and actual model orchestration
remain unimplemented. A private repository exists; the complete agreed paid
product does not follow from that fact. This assessment sampled its first-party
documentation, not all commercial implementation paths.

Required documentation alignment:

1. [FUNCTIONAL_SPEC.md](../FUNCTIONAL_SPEC.md), especially FR-15, FR-34, FR-37,
   FR-41 and acceptance journeys, still describes numeric-seniority fallback,
   consensus/timeouts and broader features as undifferentiated requirements.
   Split v0.1/free, coming-soon and private-paid behavior.
2. Organization guidance says peers must reach consensus; free now blocks
   disputed tasks. Paid voting is majority after hearing dissent, rather than
   implied unanimity or rank alone.
3. Legacy connection/help prose describes local installed CLI/direct SSH use;
   current execution requires the isolated approved worker. Fix the prose,
   not the security boundary.
4. Recovery backlog/operations paragraphs lag newer implemented reconciliation
   and protected metadata. Preserve historical notes but identify authoritative
   current capability documentation.
5. SOC 2 readiness has no verified completion evidence in this assessment.
   Keep operational/compliance work as an explicit future workstream. Core
   authentication, authorization, audit and isolation remain free and mandatory.

The existing completion rule still applies to implementations: meaningful mocked
tests, full user/technical documentation, and server-enforced permission-aware
flags with both states tested. Mandatory security boundaries have no off switch.
This assessment itself is documentation and needs no product toggle.

## Recommended implementation sequence

1. **Recover a buildable integration baseline.** Resolve the owned launch-signature
   work, reconcile the hardened audit slice and remove competing assembly paths
   through coordinated review. Run full required checks.
2. **Complete one secure execution path.** Wire authenticated scoped callbacks,
   preserve human/company provenance, enforce aggregate limits, capture artifacts
   and prove both containers stop. Validate pinned Codex and Claude adapters;
   add llama.cpp under the same applicable boundaries. Keep unsupported modes unavailable.
3. **Complete the free coordination loop.** Persist governing appointment and
   bounded delegation; add decision/approval/objection records, blocked states
   and dependency handling. Enforce irreversible-action approval at execution,
   not through prompt promises.
4. **Add bounded automatic recovery.** Build on existing journals, receipts and
   reconciliation. Define reconnect/resume versus retry, preserve committed
   outcomes and prevent duplicate effects; surface unresolved ambiguity.
5. **Align distribution and demonstrate v0.1.** Reconcile free multi-human legacy
   behavior, revise spec/help, add coming-soon entries and verify the acceptance
   journey on a clean supported self-hosted setup. Gate hosted launch separately.

Release evidence: two agents with different personas discuss a task; governing
delegation creates bounded assignments; work executes in credential-separated
containers; an objection blocks the affected task; the human resolves/approves;
artifacts and observed checks are available; the instruction/decision/action chain
is inspectable; disconnect recovery does not duplicate effects. Required provider
and supported worker topology coverage must be demonstrated explicitly.

## Verification and limits

This assessment used source/tests/docs and repository metadata, not production
sessions. No credentials were inspected, provider agents launched, databases
connected, schemas created or deployment changed.

- Initial sandbox attempts: `make test` **1.58s**, `make check` **1.96s**, both
  blocked by Go build-cache access; these are not test failures attributable to code.
- Retried with cache access: `make test` **0.68s**, `make check` **1.98s**, both
  failed at the signature compilation errors above. Some unaffected Go packages
  were cached. `make check` stopped in its race-test prerequisite; vet/Python/UI
  checks did not execute in that run.
- Earlier passing checks in the isolated audit worktree belong to that separate
  source snapshot, not the shared development baseline.
- Full automated suite coverage of the current shared snapshot is therefore
  unavailable. Live provider bridge, paired rootless runtime, hosted worker
  onboarding, actual deployed DB privileges and enterprise compliance were not
  verified. Existing synthetic tests are useful evidence of components only.

No application implementation was changed, committed or pushed by this assessment.
