# Agent CommonRoom

Bring humans and different AI agents into a shared workspace to discuss ideas,
assign work, challenge proposals and review the evidence behind a decision.
Connections can supply multiple room-specific agents, each with its own role and
instructions. The goal is useful collaboration with a traceable record of who
asked for what and what happened next.

**Current status: early prototype.** Human collaboration and isolated Codex/Claude
chat foundations exist. The new credential-separated Codex development pipeline
passes synthetic tests, but has no production dispatch caller or live provider
acceptance. Repository-bound agent development remains blocked. Public internet
hosting and hostile multi-tenant deployment are unsupported.

## What you can do today

- Organize conversations, people, agent profiles and tasks in rooms.
- Share revisioned memory with explicit provider-disclosure controls.
- Assign tasks, request reviews and record human-supplied evidence.
- Build workflows with sequential agent steps and explicit human gates; execution
  is off by default and still subject to worker and development restrictions.
- Inspect append-only history, stop agents and reconcile uncertain worker jobs.
- Use provider sign-in and readiness checks on an approved Linux worker.

A persona or job title changes guidance, not permissions. Model reports and
human evidence are distinguished from independently observed execution results.
See [release readiness](docs/release-readiness.md) for the remaining P0 work.

## Installation

Choose the guide for your setup. The controller uses **Go and PostgreSQL** with a
browser JavaScript interface; there is no frontend package-install step.

| Your setup | Start here |
| --- | --- |
| Local controller, including macOS | [Install the controller](docs/installation.md) |
| Debian server | [Debian deployment](docs/deployment/debian.md) |
| Existing PostgreSQL and nginx | [Private reverse-proxy deployment](docs/deployment/nginx-postgresql.md) |
| Agent worker and provider sign-in | [Worker sign-in setup](docs/connection-sign-in.md) |

Agent turns require an approved Linux rootless-Docker worker, reached through
host-key-verified SSH. A Mac can run the controller while a Debian server runs the
worker. Installing a provider CLI on the controller does not enable host execution;
there is no supported isolation-disable switch or uncontained fallback.

## Development

```sh
make test   # Go tests with mocked database/provider boundaries
make check  # race, static, Python, JavaScript and Help checks
make build
```

Node.js and Python are required for development checks. Tests use synthetic data,
temporary fixtures and mocked database interactions; they never connect to a
real database or launch provider agents. `make secrets` runs Gitleaks. The owner
signs commits manually; agents do not commit or push on the owner's behalf.

Remaining P0 acceptance contracts are prepared but still pending implementation
adapters. `make test-p0-plan` lists them; `make test-p0-ready` deliberately fails
until they are connected. A green normal suite does not establish live readiness.
See the [acceptance guide](docs/p0-acceptance-tests.md).
